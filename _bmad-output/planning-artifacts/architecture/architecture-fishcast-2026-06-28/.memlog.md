- (decision) Paradigm: separate scheduled pipeline (ingestion + estimation/forecasting) writes results to shared storage; web app reads only, never computes forecasts inline. Binds: FR-1..FR-4, FR-8. Prevents: forecasting logic duplicated or drifting between a request-time path and a batch path.
- (decision) Language: Python for the pipeline, confirmed by user. Web app language open.
- (decision) Deployment target: web app on Vercel (user-stated). Pipeline does NOT run as a Vercel cron function — Vercel serverless caps (10s Hobby/300s Pro execution, daily-only Hobby cron, best-effort at-least-once delivery) are a poor fit for ingestion retry/backoff (FR-1) and the estimation job. Pipeline instead runs as a scheduled GitHub Actions workflow, writing to a shared Postgres (Neon/Supabase) that the Vercel web app reads from.
- (decision) Estimation core: pipeline shells out to R (subprocess) for PE/BSS estimation methodology, reusing WDFW's wdfw-fp/CreelEstimates + creelutils R/Stan code directly rather than reimplementing in Python. Binds: FR-3, FR-4. Prevents: methodology drift from WDFW's validated approach. Consequence: GitHub Actions pipeline job needs an R + Stan (cmdstanr/rstan) toolchain alongside Python; Python orchestrator and R estimation step need a defined data interchange format (deferred: format TBD).
- (decision) Monorepo: Django web app, Python pipeline orchestrator, and R estimation scripts in one repo, separated by directory. Binds: all. Prevents: web app schema drifting from what the pipeline actually writes.
- (decision) Python<->R interchange: flat files (Parquet/CSV) via a temp directory. Python writes prepared input, invokes Rscript as a subprocess, R writes its output to a file, Python reads it back and persists to Postgres via Django ORM. Binds: FR-3, FR-4. Prevents: process coupling/fragility from an in-process bridge (rpy2) in a CI runner.
- (decision) Idempotency: every raw/normalized/estimate/projection row keyed by (fishery, date, source); pipeline writes use upsert (INSERT...ON CONFLICT DO UPDATE). Binds: FR-1, FR-2, FR-3, FR-4. Prevents: duplicate rows on rerun/retry/backfill.
- (decision) Environments: single production environment (one Postgres via Neon or Supabase + one Vercel production deployment) + local dev. No dedicated staging; Vercel preview deployments cover ad-hoc review. Revisit if schema changes ever need verification against prod-shaped data before touching the Manager View.
- (decision) Data model confirmed: Fishery, Season, SpeciesThreshold, RawCreelRecord, NormalizedCreelRecord, EnvironmentalReading, HarvestEstimate, ForecastProjection, ShareSummarySnapshot. AccuracyRecord (FR-8) is NOT a stored table -- it's a query joining ForecastProjection.target_date against the later-landing HarvestEstimate for the same date/fishery/species. User confirmed.
- (decision) Source tree confirmed: monorepo with config/, apps/{fisheries,ingestion,estimation,dashboard}/, r/ (PE/BSS scripts), templates/, static/, .github/workflows/{pipeline.yml,ci.yml}. User confirmed.
- (decision) No separate API/JSON layer for v1: chart interactivity backed by data embedded in server-rendered page, not a fetch endpoint. Binds: FR-4, FR-7, FR-8 UI. Prevents: a parallel API surface drifting from the page's own data. User confirmed.
- (decision) No background task queue for v1: Share Summary generation (the one on-demand web-app write) runs synchronously in the request (snapshot + return link); no Celery/RQ. User confirmed.
